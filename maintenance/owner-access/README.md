# Owner Access 补丁维护指南

本指南面向用户 fork：<https://github.com/BeiJiaan/dsh-web>，维护分支为 `bja-owner-access`。基线为上游正式版本 `v0.4.16`，提交 SHA：`b764700c0d039e10ff3ee60b91ce990222e7a258`。

这里集中维护两个最小源码补丁及已经实现的隔离构建流程，不是生产配置或自动部署入口。构建会运行 Host 回归测试、类型检查、编译、模板完整性校验，再生成两个可安装包。生产环境仍由管理员选择维护窗口安装；本流程不会自动替换当前插件或重启服务。

## 1. 范围与边界

最小源码修改只覆盖两个补丁包所需的宿主逻辑：

- `web-ui-session-archive`：会话归档相关的鉴权适配，复用官方认证身份与访问边界；不得引入代理伪造身份或认证绕过。
- `web-ui-usage`：用量功能所需的宿主修复，复用官方认证能力；具体行为与授权边界以经审查的补丁和测试为准。

设置桥接（settings bridge）属于 profile 配置，不是第三份源码补丁。它与远程访问开关都应由部署者单独维护，不能混入源码、模板包或发布归档。

仓库中不得提交实际部署域名、密钥、Token、Cookie、生产 profile、生产 Nginx 配置或其他生产专用配置。文档和测试只使用占位符、假数据或脱敏样例。个人 profile 与反向代理配置的备份必须保存在 Git 仓库以外的私有位置。

**任何构建、安装、升级或回滚都不得自动重启生产服务。** 维护人员必须先安排维护窗口，评估停机和会话影响，再按现场流程人工执行必要的停止、启动或重载。

## 2. 构建与官方浏览器模板

### 前置条件

- 构建机使用 Node.js **>= 24.11**（CI 固定 26.10.0）、npm、Git、GNU 兼容的 `tar`；插件运行要求仍沿用上游。
- 已安装且版本与发布元数据一致的官方 DSH（当前 `0.2.2-rc.1`）。
- 已提交的维护工具、锁文件和发布元数据；正式构建要求 Git 工作区干净。
- 可读取目标 DSH 安装目录；下面的路径只是构建输入，不意味着可以原地改写该安装目录。
- 能获取经过版本及完整性锁定的官方 npm 模板制品。

实际构建命令（从仓库根目录执行）：

```sh
npm ci --prefix maintenance/owner-access/tools --ignore-scripts
node maintenance/owner-access/build.mjs --dsh-root /usr/lib/node_modules/@deepseek-ai/dsh
```

第一条命令只安装隔离维护工具的锁定依赖，禁用依赖安装脚本；不要用根目录安装或修改上游依赖声明来代替它。构建暂存区、缓存和 dist 都被 Git 忽略。`--allow-dirty` 仅用于本地演练，产物会带 `dirty` 标记及独立目录名，不应用于部署。

也可以在 GitHub **Actions → BJA owner-access packages → Run workflow** 构建；成功后下载包含两个 tgz 和 manifest 的 artifact。工作流使用固定 Node/SDK 和锁文件，不会部署、不使用生产密钥、不发布 npm。维护分支相关改动推送时也会运行。为避免个人 fork 意外运行上游的定时任务、商店部署、发布或协作者分配，GitHub 中继承的其他工作流已停用；其源码保留，未来有需要可在 fork 中审查后重新启用。

构建流程必须满足以下契约：

1. 准备独立 staging 工作区，不在生产安装目录或当前源码树中原地打补丁、安装或覆盖文件。
2. 对两个宿主补丁执行适用的检查、测试、构建和打包；任何阶段失败都不得产出可发布的 dist。
3. 从 npm 获取**官方 0.4.16、未修改的浏览器 bundle**，校验发布元数据中固定的包版本与 integrity/hash，然后复用其浏览器产物。不得使用未锁定的 `latest`、第三方重打包制品或现有机器上来源不明的前端文件。
4. 只在隔离 staging 中完成组装；上游源码中的 package manifests 保持不变，不为本地打包改写其版本、依赖或 SDK 声明。
5. 只有所有必要测试与完整性检查通过后，才将本次完整制品提升到版本化 dist；失败时不得留下会被误认成本次成功发布的半成品。

这种模板方案**不支持直接修改前端源码后仍复用旧浏览器 bundle**。如需前端修改，必须先调整构建流程，明确前端构建、依赖锁定、SDK 兼容性和测试策略，再审查发布；不能仅编辑前端源码就宣称修改已包含在制品中。

### 输出与可追溯性

输出目录（只有两个包全部验证成功后才原子提升到这里）：

```text
maintenance/owner-access/dist/<version>-<git短SHA>/
  <session-archive-bundle>.tgz
  <usage-bundle>.tgz
  manifest.json
```

尖括号表示由构建脚本确定的版本或文件名，不是可直接复制的实际路径。每次发布必须恰有对应两个补丁的 tgz，以及可审计的 `manifest.json`，至少记录：

- 发布版本、两个制品文件名及校验和（例如 SHA-256）。
- fork 的构建 Git SHA、上游版本与基线 SHA。
- 官方模板包的精确版本、来源及 integrity/hash。
- SDK 版本或兼容性声明，以及构建时验证的目标 DSH 版本。

安装前执行只读校验（把目录替换为实际产物路径）：

```sh
node maintenance/owner-access/verify.mjs maintenance/owner-access/dist/<version>-<git短SHA>
```

它检查两个包的 SHA-256/SHA-512、版本、Git SHA、未修改浏览器 bundle 的哈希，以及覆盖行是否正确；拒绝 dirty 演练包。校验成功不等于自动授权安装，仍需确认 artifact 来自你信任的 fork/提交。发布制品不包含生产配置或敏感信息。

本流程只生成本地 tgz，**不执行 npm publish，也不发布到 npm registry**。如需传递制品，使用另行批准的受控渠道。

## 3. 安装、覆盖关系与配置

### 安装前检查

1. 在目标 profile 的插件管理器中记录 aggregate 官方插件集合、两个目标 bundle 和其他相关插件的安装状态与版本。
2. 私下备份 profile 和 Nginx 等部署配置，保留上一版两个 tgz 及其 manifest；备份位置不得纳入 Git。
3. 核对目标 DSH、SDK、补丁版本与制品校验和，安排维护窗口。
4. 明确记录两个直接补丁 bundle 的实际包标识与来源，避免误删 aggregate 或其他插件。

**保留 aggregate 已安装状态。** 两个补丁 bundle 使用其对应的 `web-ui-session-archive` / `web-ui-usage` 覆盖关系替换目标实现，而不是卸载整个 aggregate 或并行加载两套实现。安装后要验证每个目标功能只有一个有效实现，尤其不能出现重复调度器、重复任务注册或重复后台计时器；其他 aggregate 插件应保持正常。

### 通过 GUI 安装

优先使用目标 DSH 的 GUI 插件管理器：

1. 打开目标 profile 的插件管理页面，确认当前 profile 与现有 bundle 标识。
2. 如果以前安装过**同名的本地直接补丁 bundle**，先移除这些旧的直接 bundle，再从本次验证过的 tgz 全新安装两个补丁。不要假定同名文件安装会可靠覆盖旧包或清除旧入口。
3. 使用插件管理器支持的本地包安装入口或本地包路径安装本次两个 tgz；具体控件名称以当前版本界面为准。
4. 确认 aggregate 仍安装、覆盖关系正确，并检查插件状态、错误日志和功能行为。

先移除再安装可能产生短暂的功能缺口，因此必须在维护窗口进行。若采用安装器，必须先审查它是否准确识别旧的直接 bundle、正确处理同名替换和失败恢复、保留 aggregate，且不自动重启生产。未经审查不能用安装器替代这些检查。

本文不提供未经核验的精确 CLI 命令。若改用受支持的 `dsh plugin` CLI，必须先在目标版本执行并阅读实际的 `--help`（包括相关子命令），确认本地 tgz 安装、移除、目标 profile 和替换语义后再操作；不能从其他版本文档猜测命令参数。

### 认证与配置保持分离

- 使用官方认证机制验证身份与访问权限，不依赖反向代理伪造用户身份。
- `allowAuthenticatedRemote: true` 是**独立的、显式 opt-in profile 配置**，不会因安装补丁而自动开启；先评估访问边界再由管理员单独配置。
- settings bridge 也在 profile 配置层维护。不要为了迁移配置去修改源码或模板产物。
- 安装后分别验证已认证远程访问、未认证访问拒绝、归档功能和用量展示；不得把“页面能打开”当作鉴权测试通过。
- 如插件管理器提示变更尚未生效，按其提示安排人工维护操作。不要自动重启、热替换生产进程或擅自更改代理规则。

## 4. 同步上游与发布流程

上游同步以**明确审查的稳定 tag**为单位，不盲目追随开发分支、`dev` 或 `latest`。升级到较新 DSH 后，也不能继续默认使用官方 0.4.16 浏览器模板；必须重新确认兼容性并有意更新锁定信息。

建议人工流程：

1. 检查工作区状态、远端地址与现有基线记录；有未提交改动时先人工处理，不自动丢弃。
2. 从已确认的 upstream 获取选定稳定 tag，核对 tag 对应提交与版本来源。
3. 从 `bja-owner-access` 建立用于此次升级审查的分支，合并选定 tag，采用 `git merge --no-ff <stable-tag>` 保留合并边界。此处是流程说明，不授权工具切换分支或执行合并。
4. 人工解决冲突，重新审查两个最小宿主补丁、官方鉴权行为、aggregate 覆盖逻辑和调度器唯一性。
5. 检查上游 SDK 与模板结构变化，运行必要测试与隔离构建验证；重点检查官方前端模板是否仍与宿主补丁兼容。
6. 验证通过后，更新 `maintenance/owner-access/release.json`：上游 tag/SHA、官方模板包的精确版本与 integrity/hash、兼容 SDK 信息及新的发布号必须一致。元数据变更后应再按最终元数据构建、校验，确保制品确实使用新的锁定值。
7. 人工检查差异与最终制品，创建普通提交，再按仓库维护策略推送。不得省略审查或把失败构建作为发布依据。

这里不自动执行 rebase、reset、删除分支或 force-push。遇到冲突或版本不兼容，应停下来处理，而不是覆盖历史。基线分支和 tag 用于标记可追溯起点及已验证版本；建立或变更这些引用需人工明确决定，不因执行构建而自动发生。本指南不要求创建 PR。

升级时应**有意更新 pinned manifest/模板锁定记录**，不能让下载地址或哈希静默漂移。建议用 CI 校验发布元数据、模板 integrity、宿主测试、SDK 兼容性、两个 bundle 的覆盖关系及制品内容；模板或构建流发生变化时，CI 也应一并更新。

## 5. 验收与回滚

上线验收至少包括：

- manifest 与两个 tgz 的校验和匹配，版本、Git SHA、SDK 和模板来源可追溯。
- aggregate 仍安装，两个补丁各自有效，没有重复调度器或后台注册。
- 官方认证工作正常，未认证请求没有因补丁得到额外访问权限。
- `allowAuthenticatedRemote` 和 settings bridge 的实际配置符合本 profile 的明确选择，没有被安装流程偷偷改写。
- 归档和用量功能通过测试，相关日志无新的加载或兼容性错误。

失败时使用上一版已验证的两个 tgz 回滚，按同名直接 bundle 的移除/全新安装规则恢复，并按需要从**仓库外私有备份**恢复 profile 与 Nginx 配置。回滚同样需要维护窗口，不自动重启服务；完成后重新验证认证、功能和调度器唯一性。

只要官方认证已经可用，回滚或排障都**不要重新引入代理身份伪造**，也不要以关闭认证来换取功能恢复。若无法安全恢复，保留故障证据并暂停上线，先解决兼容性或配置问题。
